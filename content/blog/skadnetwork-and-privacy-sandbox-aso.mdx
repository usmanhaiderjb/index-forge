The days of deterministic device-level attribution (IDFA tracking across apps) are over.

On iOS, **Apple's SKAdNetwork (SKAN 4.0 / AdAttributionKit)** governs paid mobile attribution through delayed, privacy-thresholded postbacks. On Android, **Google Privacy Sandbox for Mobile** is introducing Privacy-Preserving Attribution (ARA) and Protected Audience APIs.

For ASO and growth teams, this privacy shift created a massive operational problem: **paid ad networks now report install cohorts on delayed, aggregated timelines, while App Store Connect and Play Console report real-time store downloads**.

In this guide, we break down the mechanics of SKAN 4.0 postbacks, explain conversion value lock-in windows, and show how to isolate true organic installs from noisy paid campaign cohorts.

```
+-----------------------------------------------------------------------------------+
|               SKADNETWORK 4.0 THREE-POSTBACK WINDOW TIMELINE                      |
+-----------------------------------------------------------------------------------+
|  POSTBACK 1 (Window 0–2 Days)                                                     |
|  ├── Measurement Window: 0 to 48 Hours                                            |
|  ├── Value Grain: Fine (0–63) or Coarse (Low/Medium/High) if threshold met        |
|  └── Random Timer Delay: 24 to 48 Hours before postback transmission              |
|                                                                                   |
|  POSTBACK 2 (Window 3–7 Days)                                                     |
|  ├── Measurement Window: Day 3 to Day 7                                           |
|  └── Value Grain: Coarse only (Low/Medium/High) + 24–144h random delay            |
|                                                                                   |
|  POSTBACK 3 (Window 8–35 Days)                                                    |
|  ├── Measurement Window: Day 8 to Day 35 (Measures 30-Day LTV / Churn)            |
|  └── Value Grain: Coarse only + 24–144h random delay                              |
+-----------------------------------------------------------------------------------+
```

## The 3 Structural Challenges of SKAN for ASO

### 1. The Multi-Day Random Delay Distortion
When an ad network delivers an install, Apple does not fire the attribution postback immediately. It adds a randomized 24-to-48-hour delay for Postback 1, and up to 144 hours for Postbacks 2 and 3.
* If you run a major paid marketing burst on Friday, your ad network dashboard may show zero installs on Friday night, a trickle on Saturday, and a massive surge on Tuesday morning.
* Meanwhile, your App Store Connect telemetry records all installs on Friday.
* **If you naively compare Friday's ad spend against Friday's reported paid installs, your calculated Cost Per Install (CPI) will look falsely inflated.**

### 2. Crowd Anonymity & Tier Masking
Apple enforces **Crowd Anonymity Tiers** (Tiers 0, 1, 2, and 3). If a paid campaign does not generate enough volume in a single time window to clear the privacy threshold:
* Apple zeroes out the fine conversion value (`0–63`).
* Apple truncates the 4-digit source identifier to a 2-digit coarse ID.
* Small campaigns fail to report granular post-install event data.

### 3. Google Privacy Sandbox Attribution
Google's Privacy Sandbox on Android mirrors this direction: eliminating GAID (Google Advertising ID) in favor of Attribution Reporting APIs with aggregated summary reports and noise injection.

## How to Reconcile Organic vs Paid Installs Under SKAN

Because paid postbacks arrive days late and contain privacy noise, you cannot rely on ad network reports to calculate your organic traffic.

Instead, implement **Top-Down Store Attribution Reconciliation**:

```
+-----------------------------------------------------------------------------------+
|               TOP-DOWN SOURCE OF TRUTH RECONCILIATION                             |
+-----------------------------------------------------------------------------------+
|  App Store Connect Daily Reported Units (Ground Truth Total)                      |
|                                 │                                                 |
|                                 ▼                                                 |
|  MINUS Verified Direct Paid Installs (ASA Search Terms + Settled Ad Networks)     |
|                                 │                                                 |
|                                 ▼                                                 |
|  EQUALS DERIVED ORGANIC INSTALLS (True Search & Browse ASO Traffic)               |
+-----------------------------------------------------------------------------------+
```

```
Daily Derived Organic Installs = Total Store Units - (Settled Paid Installs within Reconciled Window)
```

| Attribution Rule | Technical Implementation | Why It Matters |
| :--- | :--- | :--- |
| **Enforce Source Precedence** | The billing console (App Store Connect / Play Console) is the authoritative total. | Ad networks frequently double-count cross-channel conversions. |
| **Withhold Incomplete Windows** | Do not calculate the organic split for the last 48 hours. | SKAN postbacks are still in the randomized delay pipeline. |
| **Reconcile at Storefront Level** | Split by country before applying formulas. | Blended global totals hide regional cannibalization. |

## Conversion Value Modeling for ASO Teams

To ensure your paid campaigns calibrate properly without blinding your organic telemetry, configure your 6-bit fine conversion values (`0–63`) to reflect **True User Intent Milestones**:

```
[6-Bit Conversion Value Schema (0–63)]
├── Values 0–15:  Completed Onboarding & Permissions (High Intent)
├── Values 16–31: Trial Started / First Content Consumption
├── Values 32–47: High-Frequency Core Loop Action (D1 Active User)
└── Values 48–63: Direct In-App Purchase / Annual Subscription Conversion
```

By standardizing conversion milestones across both iOS and Android, your marketing team can optimize paid campaigns while your ASO team tracks true organic lift.
